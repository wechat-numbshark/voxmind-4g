## 一、为什么是 TypeScript 而不是 Python

**决定性因素是 ASR 走云 API 还是自建。**

Python 在这个项目里唯一的硬优势是语音 ML 生态（FunASR、faster-whisper 只有 Python 绑定）。
但这个阶段**不应该自建 ASR**：中文识别用阿里云/腾讯云/讯飞的 API，准确率高于自建 Whisper，
而且不用养 GPU。**一旦 ASR 走 API，Python 的优势归零。**

剩下的全是 I/O 编排——收音频流、调 Claude、发 MQTT、收飞书回调、带过期的状态队列，这是 Node 的主场。

另外两条更实在的理由：

1. **`src/types.ts` 是设备、云端、飞书三方的唯一契约。** 这套协议很碎
   （三级分类 × 双通道 × 过期规则），任何一端改了字段另外两端编译期报错。
   `tsconfig` 开了 `strict` + `exactOptionalPropertyTypes` + `noUncheckedIndexedAccess`，
   把"忘了处理 undefined"这类 bug 挡在运行前。
2. 飞书有**官方** Node SDK（`@larksuiteoapi/node-sdk`），不是社区包。

**代价（提前知道）**：以后要做自建/端侧 ASR 或音频 ML，得单独起一个 Python 微服务用 HTTP 接进来。
不要为了那一天现在就把整个云端写成 Python。

## 二、数据流

```
设备 ──Opus分块──► POST /v1/recordings
                          │
                    ffmpeg 解码 → 16k PCM        ⚠ 不用 Node 原生 opus 绑定，
                          │                        跨平台编译经常炸，直接 shell 调 ffmpeg
                     ASR（云 API）
                          │
                   Claude 意图抽取
                   （claude-opus-5 + 结构化输出 + prompt caching）
                          │
                  ┌───────┴────────┐
         置信度分流              分级查表
         ≥0.85 双通道           KIND_TIER[kind]
         0.6~0.85 只飞书        （不采信模型判的级别）
         <0.6 不推
                          │
              ┌───────────┴───────────┐
        MQTT → 设备              飞书机器人卡片
        （★只有30秒窗口）        （异步，无时限）
                          │
                  任一边点了 → 另一边立即撤回
```

## 三、三条不能改错的规则

### 规则 1：分级由代码查表，不采信模型

```ts
const tier = KIND_TIER[action.kind];   // ← 查表，不是 LLM 输出的字段
```

LLM 只负责判**动作类型**和**置信度**。级别（A/B/C）由 `types.ts` 里的固定映射决定。
这样即使模型判飘了，也不会把"给老板发消息"当成 A 类直接执行。

**如果让模型自己输出级别，某次幻觉就会变成一条发出去的消息。** 这是不可逆的。

### 规则 2：置信度分流 —— 宁可漏，不可错

| 置信度 | 通道 | 理由 |
|---|---|---|
| ≥ 0.85 | 设备 + 飞书 | 敢打断用户 |
| 0.60 ~ 0.85 | **只飞书** | 设备端弹卡片是"打断"，成本很高；飞书是异步的，成本低 |
| < 0.60 | 都不推 | 只在转写文本里高亮，用户回看时自己决定 |

提示词里明确写了「不要为了让动作被执行而虚报置信度」，并说明了分数的后果——
打分偏高的直接结果是用户被垃圾卡片淹没，然后关掉这个功能。

### 规则 3：30 秒唤醒窗口是硬约束

设备上传完成后只保持唤醒 **30 秒**，之后 4G 进 PSM，
下次能收到推送要等一个 TAU 周期（默认 1 小时）。

所以 **ASR + 意图抽取必须在 30 秒内跑完**。跑不完不是失败，是降级为"只推飞书"，
设备等下个周期。`pipeline.ts` 会打日志标出超窗的情况。

**这个窗口是"有网了马上处理"能不能成立的前提。** 想缩短延迟就把 PSM 的 TAU 调短，
代价是待机电流上升——没有标准答案，要按实际使用频率实测后定。

## 四、Claude 用法要点

```ts
const response = await client.messages.parse({
  model: "claude-opus-5",
  thinking: { type: "adaptive" },
  system: [{ type: "text", text: SYSTEM_PROMPT, cache_control: { type: "ephemeral" } }],
  output_config: { format: zodOutputFormat(ExtractionResult) },
  ...
});
```

| 做法 | 为什么 |
|---|---|
| **结构化输出**（`zodOutputFormat`） | 不解析自由文本。解析失败时按"无动作"处理，不猜 |
| **prompt caching** | 系统提示词是稳定前缀，只有转写是变的。⚠ 别在提示词里拼时间戳/用户名，会让缓存整体失效 |
| **adaptive thinking** | 判断"这句话是不是指令"需要推理，不是模式匹配 |
| 监控 `cache_read_input_tokens` | 长期为 0 说明缓存没生效，多半是提示词里混进了变量 |

**依赖版本坑（已踩过）**：`@anthropic-ai/sdk` 的 `zodOutputFormat` 从 `zod/v4` 导入，
所以 **zod 必须是 4.x**；`messages.parse` 在 0.70.x 还在 beta 命名空间下，
**SDK 要 0.120+**。`^0.70.0` 这种写法在 0.x 上只放行补丁版本，会卡住。
