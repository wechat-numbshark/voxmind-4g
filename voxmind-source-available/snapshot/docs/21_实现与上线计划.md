## 2026-09-17 进展与当前唯一拦路的事

### 这次做完的

1. **屏幕颜色 bug 修复**：`esp_lcd_panel_draw_bitmap()` 不转字节序，RGB565 被系统性打乱（背景变紫、确认区变蓝）。已修复并在实板验证，颜色恢复正确。
2. **ASR 凭据**：用户提供的阿里云 `ASR_ACCESS_KEY_ID`/`ASR_ACCESS_KEY_SECRET` 已写入生产服务器 `/opt/voxmind/deploy/.env`。**还差 `ASR_APP_KEY`**（阿里云智能语音交互控制台"项目管理"里的项目级 AppKey，跟账号级 AccessKey 是两码事）——代码校验三者缺一就拒绝启动，所以**服务没有重启**，避免把生产服务搞崩。
3. **ML307C 4G/PPP 联网**：用 ESP-IDF 官方 `esp_modem` 组件接入，完全替换掉 `app_cloud.c` 里原来的 `esp_wifi`。ML307C 不在该组件命名支持列表（只有 SIM800/BG96/SIM7600），走的是标准 AT 指令集对应的"通用模组"路径（`esp_modem_new()`）。编译通过，串口配置从 4 段(SSID+密码+密钥)简化成 2 段(密钥)。
4. **修了一个真实崩溃循环**：4G 开机超时会被 `ESP_ERROR_CHECK` 直接 abort 整机，死循环重启。已改成 3 次重试 + 失败后退回纯本地录音（联网移到独立任务，不阻塞录音循环）——这是 docs/20 §4.2 明确要求的"音频采集绝不能被上传阻塞"。

### 当时卡住的事：ML307C 开机超时——根因已找到并现场解决，不是硬件故障

用两份互相独立的固件交叉验证过，两份都在同一处报同样的错：`PIN_MODEM_PWRKEY` 拉高后，`PIN_MODEM_STATUS` 20 秒内不回高电平。这排除了"这次代码改动引入的问题"，但**不是元器件损坏**——板子当时只接 USB、没插电池。

查 TI BQ24074（板上的充电/电源通路管理芯片）官方数据手册 + 对照 BOM 的 R1/ILIM 阻值，USB 单独供电时输入电流上限被架构性限制在约 860mA，而 ML307C-GC 开机瞬间/发射突发电流需要约 1-2A——USB 供不上这个峰值，`PWRKEY` 拉高后模组根本起不来，`STATUS` 自然不会回高。BQ24074 的电源通路设计本来就要求电池在场以补足这段峰值电流，这不是可选项。

**2026-09-17 晚间实测确认**：用户接入一块 3.7V/1050mAh 两线 LiPo 电池到 `J1`（电池只有 2 根线、连接器和板上 3-pin JST-PH 不匹配，剪掉原连接器、用万用表以 `R4=10kΩ`（TS 脚特征电阻）为基准现场测出 GND/TS/VBAT+ 三个 pad 后直接焊接裸线），电池接上后立即点亮屏幕、`modem_power_on` 成功、UART 正常交给 esp_modem、PPP 拨号命令成功下发。**至此确认根因诊断正确，问题已解决，不是硬件故障、不需要返工焊接。**

同一份自检固件之前报告 **11/13 项通过**（PSRAM、电量计、SD卡、双麦、屏幕八色测试条、马达全部正常），触摸芯片显示"已响应 chip_id=0xb6"但标记失败——大概率是自检等待人手触摸屏幕的 10 秒窗口里没人去碰，不是真故障，未继续跟踪。

### 2026-09-18：APN 自动识别 + 端到端 4G 联网打通

用户确认设备里插的是中国电信卡，此前固件硬编码 `AT+CGDCONT` 用的是移动的 `cmnet`，注网 30 秒超时正是电信卡配错 APN 导致，不是"没插卡"的伪告警。改为按 SIM 的 IMSI（`AT+CIMI`，取前 5 位 MCC+MNC）自动识别运营商选 APN：移动 46000/02/04/07/08/13→`cmnet`，联通 46001/06/09/10→`3gnet`，电信 46003/05/11/12→`ctnet`；识别不到时退回 `CONFIG_VOXMIND_APN`（Kconfig 默认值，现在只是兜底，不再是主路径）。

实测过程中又挖出两个真实 bug，都已修复：

1. **`modem_power_on()` 对"STATUS 已高"盲目信任**：PWRKEY 是脉冲不是电平开关，MCU 侧复位（多次刷机/看门狗）不会让模组跟着断电重开。如果上次是在 PPP 拨号中途复位的，模组会停在数据模式，直接当"已就绪"会导致后面所有 AT 指令全部超时或收到乱码。修复：STATUS 高时先探测一次 AT，探测失败就不再假设任何"半恢复"状态可信，直接强制关机重开一次换干净状态。
2. **刚开机完成时 AT 服务栈还没完全稳定**：即使 AT 探测已经拿到 OK，紧接着的 `AT+CPIN?`/`AT+CIMI` 有时会收到二进制乱码而不是超时/ERROR。修复：开机完成后加 1.5 秒稳定延时，且这两条关键指令各自带重试（最多 3-4 次），不再一次失败就退回默认 APN。

修完后实测完整走通：`IMSI前缀=46011 → 中国电信，APN=ctnet` → PPP 拨号 → `IP_EVENT_PPP_GOT_IP`，拿到公网地址（具体地址已从发布副本移除）→ HTTPS 证书校验通过 → 音频块上传到生产服务器，`docker logs voxmind-api` 确认 `PUT /v1/device-sessions/.../chunks/0` 和 `chunks/1` 均返回 **201**（其中 chunk 1 第一次上传因为设备被刷机重启打断，重启后自动重传第二次成功，验证了幂等重传不产生重复/损坏）。**这是本项目第一次跑通"实板 4G 断点续传到云端"的完整链路。**

## 2026-09-19：Opus、设备界面、语音识别与三个丢录音的真问题

### 这次修掉的真问题（都不是"代码写完"，是实测抓出来的）

1. **一直在丢约 6% 的录音，没人发现**：I2S 只有 90ms 硬件缓冲，且读麦和落盘在
   同一个循环里，块边界的 fsync/rename/open 加上上传与目录扫描抢 SD 卡，一慢
   就溢出。表现是每个 5 秒块实际耗时 5.05~5.4 秒——超出的部分就是被丢掉的声音。
   改成"采集任务 + 8 秒 PSRAM 环形缓冲"后，实测采样率稳定 16000/s、累计丢失
   0ms，连续跑 111 分钟没丢一个采样点。丢失量也会被计数并由诊断报出来。
2. **上传队列会被一个 0 字节文件永久堵死**：文件名用 `sscanf("%8u.pcm%c")==1`
   判断，字面量不匹配时 sscanf 照样返回 1，正在写的 `.part` 也被当成待传块。
   上传任务卡在它上面无限重试，后面所有录音都传不上去。改成严格校验文件名。
3. **一次 TLS 握手能把录音饿死**：每个请求都新建连接，S3 没有 ECC 硬件加速，
   握手要几秒满 CPU，直接触发看门狗复位整机。改成每个任务一条长连接复用，
   一次连接只握手一次，单块上传约 0.6 秒。

另外：服务器明确拒收(4xx)的块移到 `rejected/` 留档而不是堵住队列；掉电残留的
半截 `.part` 开机时抢救成正式块（Ogg 截断也能解出截断前的声音），只有 0 字节
才删；每传一块都全盘扫目录改成按块号游标推进（离线攒下几万块时才追得上）。

### Opus 编码踩到的坑

`esp_audio_codec` 的编码器需要约 40KB 栈（README 里写了），只给 8KB 时第一帧
就踩坏相邻的 newlib stdout 锁，崩溃现场却出现在**别的任务的 printf** 里
（`vfprintf` → `__retarget_lock_acquire_recursive`），极具误导性。
定位靠的是 addr2line 解析真实调用栈，而不是猜。

### 设备界面（docs/20 §2.3–2.5、§10）

LVGL 9 + 思源黑体 GB2312 6763 字（SIL OFL，字库与生成脚本已入库）：
顶部录音状态取自"最近 2 秒真有采样进来"，不可伪造；主页显示网络/待同步/时间；
有待确认卡片时显示工具类型、1/N、标题详情与确认/取消，处理中锁定防连点。
实体键：**长按录音键安全关机**（录完当前块→断模组→深睡眠，长按可唤醒），
OK/BACK 等价于屏幕确认/取消；串口 `shutdown` 命令同样走安全关机流程。

### 语音识别与意图：改用阿里云百炼（DashScope）

用户提供的是百炼 API Key（`sk-` 开头），不是智能语音交互的 AppKey——好在百炼
一个 Key 就能同时做语音识别和大模型，比原方案少两个密钥：ASR 用
`qwen3-asr-flash`，意图用 `qwen3.8-flash`（替换原 OpenRouter 免费模型）。
