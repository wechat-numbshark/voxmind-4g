# VoxMind 屏幕、稳定性与控制效果审计

日期：2026-10-10。范围：用户两张实机照片、当前本地固件与云端源码、生产服务只读检查。本次没有修改运行逻辑、发布固件、执行空调控制或创建真实动作卡片。保留工作区原有改动。

## 结论

照片中的现象主要可以由屏幕布局代码解释，不需要通过更换服务器解决。存在两件同时发生的事：计算空间时使用上一帧高度，造成偶发重叠；暂停提示本身占据过多空间，即使高度正确也容不下回执。因此只改一个高度读取调用，还不能得到用户期望的“暂停时也看得到执行结果”。

优先级建议：屏幕确定性布局 → 回执刷新与手势一致性 → 响应字节协议 → 执行重试与确认状态 → 意图一致性与延迟测量。这里 P1 指优先修复，不代表已经发生数据丢失或设备误操作。

## 1. 照片对应的具体问题

### P1：暂停卡片与回执抢空间，且空间判断读取旧高度

证据：[ui.c](/Volumes/neo/projects/voxmind/firmware/components/ui/ui.c:732)。`rebuild_stack()` 的内容区是 y=146 到 y=270，仅 124px。暂停卡片 74px，间距 8px，回执 54px，总计 136px，不能同时完整容纳。

代码先调用 `fill_slot()` 修改高度，随后用 `lv_obj_get_height()` 算已用空间，但最终定位却使用 `lv_obj_get_style_height()`。LVGL 的前者返回已经布局好的坐标高度，不会替这次样式变更立即完成布局；[LVGL 源码](/Volumes/neo/projects/voxmind/firmware/managed_components/lvgl__lvgl/src/core/lv_obj_pos.c:605) 可以直接确认。

按源码公式做纯算术验证：

| 上一帧槽位高度 | 是否允许放回执 | 实际回执底边 | 结果 |
| --- | --- | --- | --- |
| 54px | 是：146+54+8+54=262≤270 | 146+74+8+54=282 | 压到 y=272 的提示行，符合照片一 |
| 74px | 否：146+74+8+54=282>270 | 无回执 | 只剩暂停卡片，“还有4条”仍显示，符合照片二 |

这是源码级解释，不是对实机帧日志的重放；尚未采集设备现场刷新轨迹。照片二本身不能证明回执被删除：当前布局会主动隐藏它。

另外暂停、低电、离线三个优先提示在预算检查前都可能被加入，组合状态更容易超出屏幕。

建议：先用明确的标量高度生成布局计划，再一次性应用到 LVGL；所有卡片、间距、主题边框和底部提示都纳入同一预算。暂停状态只保留录音行中的紧凑提示，避免再占用 74px 的重复卡片；有回执时至少保证一条可见。离线与低电合并成紧凑状态区，详细说明点开看。不要只调用 `lv_obj_update_layout()` 掩盖空间本身不足的问题。

### P2：录音状态行没有给长文案留宽度

证据：[ui.c](/Volumes/neo/projects/voxmind/firmware/components/ui/ui.c:1249)。继续录音提示与右侧电平条共用固定宽度，文字没有显式限宽和截断策略。“按录音键继续”约需 112px，而它到电平条之间的空间不足，符合照片里的文字与点条重叠。

建议：暂停时隐藏无意义的电平条；录音时显示时长，暂停时显示短提示；录音异常文案单独限宽。维持现有主题，不需要重做整套视觉。

## 2. 回执显示与交互稳定性

### P1：滑动完成时读的是当前索引，而不是开始滑动的回执身份

证据：[ui.c](/Volumes/neo/projects/voxmind/firmware/components/ui/ui.c:549)、[ui_set_feed](/Volumes/neo/projects/voxmind/firmware/components/ui/ui.c:1648)。动画完成回调由槽位索引重新获取 `s_slot_receipt` 和 `s_receipts`；动画期间服务器刷新可能重绑定这些数组。UI 锁只能让调用串行，不能保证整个 160ms 手势期间的数据身份不变。由此存在划 A、最终移除 B 的风险，尚未实机复现。

刷新时也需要显式处理旧动画和槽位 x/opacity，避免新内容继承旧卡片的滑动位移或透明度。

建议：手势开始快照回执 ID 和 feed generation，完成后按 ID 删除；刷新时取消并复位槽位动画，或在手势结束后应用新 feed。用“待删除 ID 集合”维持乐观 UI，服务器成功后再正式清除。

### P2：本机删除与服务器提交不是可靠事务

证据：[动作入队](/Volumes/neo/projects/voxmind/firmware/components/app_cloud/app_cloud.c:423)。`xQueueSend(..., 0)` 未检查返回值，UI 已经在本机删除回执；队列满或请求失败时，服务器可能仍保留它，后续又推回来。

建议：检查入队结果，显示可重试状态；回执删除按 ID 幂等提交，断网时保留待提交记录，不把请求失败等同于已完成。

## 3. 固件与云端数据协议

### P1：响应缓冲容量与接口允许的内容不匹配

证据：[http_response_t](/Volumes/neo/projects/voxmind/firmware/components/app_cloud/app_cloud.c:668)、[device-feed](/Volumes/neo/projects/voxmind/cloud/src/app.ts:748)。固件固定缓冲 3072 字节，其中 JSON 可用 3071 字节；接收事件对超出部分静默丢弃，没有溢出标记。云端允许 4 条回执、10 条时刻表，每条含最多 40 字标题和 60 字原话。UTF-8 中文不能按“字符数约等于字节数”估算。

纯 Node 构造接口允许的长中文内容，4 条回执+10 条时刻表共 5516 字节；按固件容量截断后 `JSON.parse` 失败。本次生产 feed 只有 1292 字节，因此不能把这项潜在缺陷归因于当前照片。

建议：定义接口最大 UTF-8 字节预算并测试，不仅限制条数；首页只发简短摘要，详情按需拉取，时刻表分页。固件增加明确 overflow 状态和日志，错误时保持上一份有效 feed；若扩大接收缓冲，先测内部 RAM/PSRAM与任务栈，不能只把栈上的数组盲目加大。`device-actions` 的 detail、reminder、command 组合也需同样做容量验证。

## 4. 执行闭环可靠性

### P1：失败动作无上限地进入执行队列

证据：[执行调度](/Volumes/neo/projects/voxmind/cloud/src/index.ts:150)、[可执行动作查询](/Volumes/neo/projects/voxmind/cloud/src/store/postgres.ts:651)、[ExecutionService](/Volumes/neo/projects/voxmind/cloud/src/services/execution.ts:11)。每 5 秒取最早 20 条 `confirmed/failed` 动作；执行服务只跳过成功和 running，没有尝试次数、退避和永久错误分类。

持续失败的动作可能反复请求；20 条旧失败也可能挤占新命令。超时不等于设备未收到：在不支持幂等的外部红外链路上，盲目重试可能重复发射。还需处理服务退出后遗留 running 的租约，以及并行调度对 queued/failed 的原子抢占。

本次生产只读检查：最近 24 小时执行表 5 条 succeeded，未见失败重试正在发生。以上为源码风险，不是已经发生的生产事故。

建议：原子 claim、执行租约、按错误类型的有限重试与指数退避、`nextAttemptAt/attempts`；永久错误进入终态，未知结果单独表达，不自动重放物理命令。人工重试应产生明确的新尝试记录。

### P1：确认时未直接检查截止时间

证据：[ActionService.confirm](/Volumes/neo/projects/voxmind/cloud/src/services/actions.ts:97)。当前只检查状态是否 expired/cancelled，过期扫描每 30 秒执行。因此存在到期但尚未被扫描的确认窗口；failed 状态也可再次确认。

建议：确认事务内校验 expiresAt 和允许的状态，执行前再校验动作时效；过期清理定时器仅负责收尾，不充当唯一截止保护。

### P2：HTTP 200 不等于正确表达执行结果

证据：[post_device_action](/Volumes/neo/projects/voxmind/firmware/components/app_cloud/app_cloud.c:1206)。固件仅根据状态码判定提交成功，没有消费响应中的执行阶段；UI 的“已确认正在执行”可能滞后于真实状态。

建议：区分“待确认 / 已确认 / 正在发送 / 指令已发送 / 失败 / 结果未知”。当前红外链路只能证明请求或命令发送，不应把接口成功表述成已经观测到空调实际开机；未来有设备状态反馈后再升级为“已验证”。

## 5. 统计与识别效果

### P2：暂停与继续会使“今日录音”本机补偿不准确

证据：[update_stats_line](/Volumes/neo/projects/voxmind/firmware/components/ui/ui.c:718)、[ui_status](/Volumes/neo/projects/voxmind/firmware/components/app_cloud/app_cloud.c:294)。录音中用“距最近云端统计的墙钟时间”补时，期间暂停也会计入；暂停时又不加已累计的本机差值。备用 `recording_seconds` 本身也是距录音起点的墙钟时间，不能直接替代有效采样时长。

建议：以有效写入音频采样数或累计有效录音时间为基准，保存拉取统计时的本机基线；暂停、断网、继续、跨日都做状态测试。避免已录时长随状态切换退回或跳增。

### 意图路由：用设备语义与结构化动作，不要只匹配关键词

语音入口已有设备 hints、控制白名单和控制/待办区分，之前误显示为待办的案例也有旧固件工具标签因素。不能据屏幕标题反推模型工具选择。

当前可改进处：网页聊天初始化未像语音入口一样注入设备 hints（[app.ts](/Volumes/neo/projects/voxmind/cloud/src/app.ts:135)、[chat.ts](/Volumes/neo/projects/voxmind/cloud/src/ai/chat.ts:97)）。建议两个入口共用设备目录、别名、可用命令和参数 schema；生成待确认卡片前就校验合法设备与能力，而不是等确认执行才报错。

应建立不触发真实设备的固定评测集：

| 话语 | 预期 |
| --- | --- |
| 打开空调 | 当前控制，已登记默认命令 |
| 不要打开空调 | 不控制 |
| 提醒我晚上开空调 | 提醒，不立即控制 |
| 空调怎么打开？ | 解释，不执行 |
| 他刚才说“打开空调” | 记录或讨论，不执行 |
| 调到26度，但只有25度场景 | 提示能力限制，不伪装26度成功 |
| 打开那台空调，有多台同类设备 | 澄清目标 |

严格、完整、能力匹配的短命令可以走快路径；否定、引用、未来时间和多目标不能靠“空调+打开”简单匹配。记录原话、工具、设备 ID、命令、判定原因，便于区分 ASR 听错、意图分类错、界面标签错和执行失败。

## 6. 性能：先测端到端，暂不需要升级服务器

生产只读采样：服务器负载约 0.08，可用内存约 817MiB，磁盘约 72%；VoxMind API、EVA 健康，Home Assistant 运行中，相关容器重启数为 0。Swap 有历史占用，但单点占用不能证明正在交换或延迟来自内存压力。设备上报固件为 1.0.23、OTA 状态 done；这只是上报状态，不代表本报告发现的修复已存在于该镜像。

容器内请求采样：device-actions 约 10ms，device-feed 约 51ms。它们不包含设备 4G、上传、ASR、模型或 HA 云链路，不能当作语音端到端延迟。

源码已有值得保留的优化：局部刷新、PSRAM双缓冲、连接复用、人声过滤，以及按住标记完整到达后立即识别。`pickRun()` 已有按住命令结束的快路径，不能把它当成尚未实现的建议。12 秒空闲等待和 20 秒标记宽限是兜底路径，不是所有命令都必定等待这么久。

下一步测量建议：为同一请求贯穿 chunk上传→VAD→ASR→标记匹配→意图→设备收到卡片→确认→HA发送的 trace ID，输出各段 p50/p95。区分正常短命令、断网补传、电视背景声、长按停顿。设备侧测最大内部可分配块、堆低水位、各任务栈余量、掉采样数、SD写入p95、UI刷新耗时与队列满次数。根据数据再调整轮询和合句窗口，不先牺牲录音完整性。

UI 可在正确布局基础上减少重复样式赋值和无变化的时刻表重建，但不要恢复全屏强制刷新；先保证输出确定且手势一致，再追求帧率。

## 7. 分批实施与验收

1. **屏幕补丁**：确定性高度预算、紧凑暂停区、文字限宽、动画ID绑定与复位。验收暂停/继续、4条回执、低电+离线、各主题边框、刷新撞上滑动；卡片不得越过提示边界，滑动不得删错ID。
2. **协议与统计补丁**：字节预算、overflow检测、保留有效feed、删除重试、有效录音计时。验收全中文长文本超过3KB、断网重连、队列满、暂停2分钟再继续、跨午夜。
3. **执行闭环补丁**：有限重试、原子claim、租约恢复、内联过期校验、真实阶段显示。用模拟执行器验收超时、永久错误、并行确认和服务重启，不直接拿真实空调做故障压测。
4. **效果与延迟**：统一设备目录、固定意图评测集、分段trace。先拿到当前基线，再定提速目标。

本次完成的是诊断与优化计划，不是修复交付。算术和JSON边界验证已运行；固件构建、实机帧观察、手势竞态复现、24小时运行和端到端延迟基线尚未完成，不能标为已验证。实施后应先测试环境回归，再打固件、实机复测与小范围OTA。
